## Repository and Codebase Organization

Our Buzzer project lets a host run a quiz on a shared screen while players answer from their phones or computers. The host can create games, edit questions, and manage course rosters. Players can join through their course access or as guests when the room allows it. The admin side handles accounts and permissions. My main parts of the project were T8 image support, the T7 Sort It and Spot It questions, the live-session reconnect fixes (B1/B2), test-data cleanup, and my two T6 games.

The frontend has three separate React and TypeScript apps for the host, player, and admin. The apps all communicate with the same backend. The server checks what each user is allowed to do.

Our backend uses Python with FastAPI. The `routers/` folder handles HTTP requests, while `websocket/` handles the live Socket.IO events during a game. The socket connection lets the server send updates as the game progresses. Both entry points use `services/`, where most of the rules and logic live. The `schemas/` folder checks the shape of incoming data, `models/` represents database records, and `migrations/` keeps track of changes to the database structure.

`tests/` contains the unit, integration, and browser checks. `sample_games/` holds importable quizzes, and `scripts/` contains tools such as the player simulator and my T6 game generator. We kept design documents in `docs/plans/` and Claude's session records were automatically placed in `ai_log/`.

Docker Compose runs our backend, nginx, MySQL, and Redis. Nginx serves the built frontend apps and passes API and socket traffic to the backend. The Compose and nginx files define how these services reach each other.

MySQL stores information we need to keep, including users, questions, images, and scores. Redis holds the current room state, such as which question is open and how many players have answered. Working on the live-session fixes helped me see why these two stores have to stay consistent. An answer can be saved in MySQL but still need its Redis count updated if something fails between those steps.

A walkthrough:

* When the host presses Start, the frontend sends `host_advance`. The server checks the host, starts the question, and sends a `new_question` event. The host and player apps listen for that event and display their versions of the question. The server controls the timer and keeps the answer key out of the question message. For Spot It, the projector receives the image, while the phone only shows the grid the player uses to choose a cell.

* When a player submits, the phone waits for acknowledgement before showing the answer as locked in. The server checks that the question is open and the player has not already answered. It calculates the score, saves the answer in MySQL, and then updates Redis. A retry can finish an interrupted update without awarding the points again in the current single-worker setup.

* When the host shows results, the server closes answers and waits for submissions already being recorded. It then combines the saved scores and answer distribution for the results screens. If those submissions have not finished, it delays the results. The next host advance either opens another question or finishes the game.

Brody created the original context hierarchy. I extended it through my T8, T7, and bug-fix work, including the [backend overview](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/backend/app/CLAUDE.md), [services context](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/backend/app/services/CLAUDE.md), [WebSocket context](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/backend/app/websocket/CLAUDE.md), and the context files for the [host pages](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/frontend/host/src/pages/CLAUDE.md) and [player pages](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/frontend/player/src/pages/CLAUDE.md). Keeping these files updated helped me connect a feature's behavior to all the places that support it, including the editor, scoring, results, and reports.

One thing I learned from this was why the current app assumes one backend worker. The gateway tracks connections, timers, and answers being processed in Python memory. Those tracking structures belong to one process, so another worker would not automatically see them. A host reconnecting to a different worker could leave the original worker thinking the host was still gone. Having Redis available does not make those Python structures shared. This is a limitation we need to address before running multiple workers.

## Design Process (Elephant/Goldfish)

I used the Elephant/Goldfish process for both the [T8 image design](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/docs/plans/t8-image-support.md) and the [T7 question-type design](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/docs/plans/t7-question-types.md). In the Elephant session, I worked through the behavior I wanted and had Claude explain the choices before we settled on a plan. For example, Spot It needed decisions about how authors choose correct cells, what players see, and what happens when an image is replaced.

I then used fresh Goldfish sessions for comprehension, criticism, and readiness checks. I brought the findings back for revisions before implementation.

T8's criticism review found a problem with database locks, recorded in §3.10 of its specification. Making two requests take turns was not enough if the second request still used information it had read before waiting. The plan had to require fresh reads after taking the lock. Otherwise a size check or a check for a live game could make its decision using old information.

T7's implementation-readiness review found a problem with replacing a landscape image with a portrait image (R5 in §10). Reconfirming the correct cells could leave the old dimensions saved on the question, which would make the grid display incorrectly. We made it explicit that every Spot It save refreshes the dimensions from the current image, even if the request only sends a new confirmation, and added a regression test for that case.

There were also findings we did not accept. T7's criticism review suggested changing how fractional points were rounded, but checking the actual outputs showed the existing approach already matched across the relevant displays. The proposed fix would have caused a mismatch. That decision is recorded as D5 in §9. The reviews helped, but their suggestions still needed checking.

I preserved the original T7 draft in [`a3a0f50`](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/commit/a3a0f5075c8b5e8d738cee7926e3dc44ba2fa662) and revised it in [`2af12a0`](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/commit/2af12a044fdec4e3207951e9ef6b817dcf12040c) after T8 provided the image support it would use. During T8 implementation, checking Pillow's behavior also showed that saving a JPEG could preserve its old comment metadata. Claude updated the specification before coding that part of the pipeline. These were reasons to revisit the plan as we learned more.

I also used design discussions and reviews for my [T6 games](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/docs/plans/t6-quiz-games.md) and the [live-session and test-cleanup fixes](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/docs/plans/fix-live-session-test-cleanup.md).

## Best Practices Learned

I learned more about keeping work separate in Git. T7 depended on T8, and the later bug fixes depended on T7. As those branches were merged, I had to bring main back into the remaining work and check that each MR showed the intended changes. One merge produced 34 conflicts because main contained a squashed T8 commit while the T7 branch still contained the original T8 commits and later T7 edits. Before resolving them, Claude checked that main's version of each conflicting file matched the earlier T8 snapshot already in the branch. That justified preserving the T7 version without discarding upstream changes. The [merge report](https://git.doit.wisc.edu/cdis/cs/courses/aicoding/fa26/student-repos/p2/buzzer-85/-/blob/93e5ed0c1bfa307c3f0c893d36b99cb3e0dc9b15/ai_log/2026-09-29_22-45-16_46755eea.md) records that comparison. I learned that choosing a side in a conflict needs evidence about what both versions contain.

I also learned that a passing test is only useful if it checks the behavior we care about. One browser check tried to prove that disconnected host controls were blocked by clicking a disabled button. The browser would not deliver that click anyway, so the test could pass without exercising the application's guard. It was replaced with a check of the messages the projector actually sent. For a regression test, removing the fix should make the test fail.

Test cleanup was another practical lesson. Repeated runs should clean up the records they create by exact ID, while preserving unrelated records. The guest API can return an existing account, so getting a successful response does not prove the test owns that guest. Our cleanup records ownership and keeps uncertain accounts. That made the test suite more useful without putting other data at risk.

Applying the Elephant/Goldfish method showed me a new and interesting way to use AI. Through this method I was able to discuss design choices and then test them in a fresh session helpped clarify my intention and what decision should be made before implementation. This development strategy seems useful and I plan to use it more in my projects.
